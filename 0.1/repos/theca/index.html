theca

theca

Theca is an encrypted container format in pure Go, with a library and a command line. The library gives an io.ReaderAt and io.WriterAt over the logical volume, and the command line creates, inspects, verifies, imports and exports containers. Since v0.2.0 it also serves the files inside over SMB and mounts them: see Serving and mounting.

The same logic is a library package, share, since v0.3.0: see Library: share.

Release: v0.25.0 (tag v0.25.0 of go-theca/theca; install with go install github.com/go-theca/theca/cmd/theca@v0.25.0). What changed is in the CHANGELOG at v0.25.0. The format may still change before v1. This page was written from v0.10.3 and the security changes of v0.24.0 and v0.25.0 are added below; where it differs from the repository, the repository wins. Its links to the repository’s design documents still point at tag v0.1.0, and the performance tables below were measured on the v0.1.0 commit.

What it is

From the README:

  • authenticated sectors: XChaCha20 xor AES-256-CTR, with HMAC-SHA-256;
  • a Merkle tree over the sector tags, and a write-ahead journal;
  • no magic bytes;
  • keyslots opened by a password (Argon2id), a recovery code, or both;
  • an optional hardware rollback counter.

The design, its threat model, the sources it rests on and the decisions taken are in docs/DESIGN.md; section 0 is a one-table summary.

Factors

A container is opened by one of three factors:

  • a password, stretched with Argon2id;
  • a recovery code, printed once by create and never stored;
  • a FIDO2 security key, which is never a factor alone: it always pairs with the password or with the recovery code.

The policy is chosen at creation. --policy any (the default) lets the password alone, or the recovery code alone, open the container. --policy 2of3 needs two of the three: password and recovery code from the start, and a FIDO2 key (enroll-key) then pairs with each.

Daily use: profiles, open, close (v0.20.0)

A long command line is the price of several factors. A profile names a container once; theca open then uses the password from the secret manager and one touch of the key, with nothing new stored anywhere:

# once: references only, nothing secret is written, nothing secret is read
theca profile add vault ~/vault/vault.theca \
    --password-from 'keepassxc:https://theca.invalid/vault' --device bio

# every day
theca open vault      # manager + one touch; mounts; frees the terminal
theca status          # what is open, where it is mounted
theca close vault     # unmounts, commits, closes
  • The profile file is containers.toml in os.UserConfigDir()/theca, mode 0600 in a 0700 directory; a file another user can read is refused. It holds the container’s path, password-from, recovery-from and pin-from (keychain:, secretservice:, keepassxc:; file: is refused), device, counter, tpm-device, tpm-auth-from, tpm-endorsement-auth-from, share, sync and close-on-lock. theca profile add checks the syntax of the references and never reads a secret; profile list and profile remove NAME list and delete (the container and the manager’s entries stay). A counter whose authValue is derived from the master key needs no tpm-auth-from; counter = "tpm" stays in the profile, because the header can be read only after the unlock.
  • open starts a background process that holds the unlocked container, serves it on a loopback address and mounts it in the file manager, then returns. The process locks the container file first, so a second open of the same container is refused before any unlock or counter increment.
  • close and status talk to that process over a Unix socket, mode 0600 in a 0700 directory ($XDG_RUNTIME_DIR/theca, else os.UserConfigDir()/theca/run), which refuses any user but the owner (SO_PEERCRED, LOCAL_PEERCRED). A message is one JSON line of at most 4096 bytes, with no unknown field; no secret crosses it. The profile parser and the socket decoder are fuzzed.
  • session.Start (v0.23.0) is what open does to start that process, as a library call: session.Start(ctx, exe, name, notice) runs exe _serve NAME with no terminal (standard input is /dev/null), waits until the container is unlocked and mounted, hands each line the process writes to its standard error while it unlocks (the security key’s touch notice) to notice, and returns the session.Info. A cancelled ctx kills the process. session.StartAttached is the terminal form theca open uses. The gui uses it for its profiles screen.
  • Auto-close (close-on-lock, default true). On Linux theca asks logind over D-Bus: Session.Lock, LockedHint, PrepareForSleep, PrepareForShutdown. On macOS (v0.22.0) it listens for com.apple.screenIsLocked, NSWorkspaceWillSleepNotification and NSWorkspaceSessionDidResignActiveNotification: no polling lag, and the container is closed before the machine sleeps. The observers are proven at start with a notification of the process’s own name; if they cannot be registered or heard, theca falls back to reading CGSSessionScreenIsLocked every two seconds (a wall-clock jump the monotonic clock did not make counts as a sleep), and theca open prints which mode is active. The container is then unmounted, committed and closed. Windows has no source yet: the container stays open until theca close. Not measured against a real lock or sleep on either system: the signals are tested with fakes, and on macOS with a real round trip of a notification of our own name.

Command line 

go install github.com/go-theca/theca/cmd/theca@latest

theca create vault.theca --size 1G            # asks the password twice, prints the recovery code once
theca info   vault.theca                      # unlock and describe
theca verify vault.theca                      # authenticate every sector and tree node
theca import vault.theca --password-from keychain:theca/vault --offset 0 < disk.img
theca export vault.theca --password-from keychain:theca/vault > disk.img

theca enroll-key vault.theca --recovery-from keychain:theca/rc   # pair the key with the password and the recovery code
theca info vault.theca --fido2                                   # password + key
theca info vault.theca --recovery-from keychain:theca/rc --fido2 # recovery code + key

  • Secrets never go in arguments or environment variables. The password is read from the terminal with echo off, or from a secret manager (next item).

  • Secret files are deprecated (v0.21.0). --password-file, --recovery-file, --pin-file, --tpm-auth-file and --tpm-owner-auth-file still work (a regular file, mode 0600 or stricter) but are hidden from the help, and each use prints a warning on standard error naming the --X-from replacement. So does a file: reference in --password-from, --recovery-from and --pin-from. --tpm-auth-from refuses file:, like the other TPM flags. A plaintext file beside a container protected by hardware keys defeats them.

  • Secrets from a reference (v0.12.0). --password-from, --recovery-from and --pin-from take a reference instead of a plaintext file, as go-authn/secretsource defines it: keychain:SERVICE/ACCOUNT (macOS Keychain), secretservice:SERVICE/ACCOUNT or secretservice:KEY=VALUE[,KEY=VALUE] (GNOME Keyring, KWallet, KeePassXC’s Secret Service integration on Linux), and since v0.14.0 keepassxc:URL (the only form since v0.15.0), the entry whose URL field is that URL (KeePassXC’s browser-integration protocol, macOS and Linux; fill the entry’s URL field, for example https://theca.invalid/vault). keepassxc:by-uuid/... and keepassxc:by-path/... are refused: KeePassXC 2.8.0 crashes on an entry without a URL. No scheme runs a command. The -file flags are unchanged and exclusive with the -from flags. KeePassXC needs Browser Integration enabled and one secretsource keepassxc associate; secretsource check REF verifies a reference without printing the secret.

    theca info vault.theca --password-from keychain:theca/vault
theca info vault.theca --password-from 'keepassxc:https://theca.invalid/vault' --fido2 --pin-from 'keepassxc:https://fido.invalid/yubikey-5c'

  • Storing the new secrets (v0.16.0). theca create --password-to REF [--generate N] [--recovery-to REF] [--replace] puts the new password and the recovery code straight into a secret manager (keychain:, secretservice:, keepassxc:URL, through secretsource store), so neither is typed into a file or left on the terminal. --generate N draws the password (letters and digits) and needs --password-to; --password-to and --generate exclude --password-file and --password-from. The password is stored before the container is created, so a failed store creates nothing. The recovery code is stored after creation; if that store fails it is printed after all (the only copy) and create exits with the error.

  • create prints the recovery code once, on standard output. If you redirect it to a file, that file gets your umask (often 0644): restrict it, or better, write the code down on paper.

  • import reads its data from standard input, so it needs --password-file or --recovery-file. It is not one atomic transaction: on an error, the bytes written before the error are kept.

  • enroll-key makes one discoverable credential on the key (relying party theca, credProtect 3, hmac-secret) and pairs it with the password, and with the recovery code too when --recovery-file names it. The key is touched twice: to register, then to confirm.

  • Pairing only adds a way in (v0.17.0). Under policy any the password alone (and the recovery code alone) still open the container after enroll-key. It says which still do and prints the command that removes the password-only slot. enroll-key --require does it in one run: after pairing, the key is touched once more to prove the password with the key opens the container, and only then is the password-only slot removed (nothing is removed if the proof fails; the pairing stays). It does not remove the recovery-only slot: that code is the way in if the key is lost, so under policy any it still opens the container alone until you run theca slots remove --remove recovery --keep password+fido2 (after which a lost key means a lost container). A recovery code that was not presented cannot be tested, and the output says so.

  • --fido2 adds the attached key to an unlock. Since v0.10.3 the key’s built-in verification (fingerprint) is used only when its GetInfo says uv is true (CTAP 2.1 6.4). On CTAP2_ERR_UV_INVALID the tries left are read and shown, and the attempt is retried up to 5 times. On UV_BLOCKED, no tries left, or no fingerprint enrolled (NOT_ALLOWED), theca says so and uses the PIN when one is set, else fails with ErrUVLocked. This is not measured on a real YubiKey Bio. A key without a fingerprint asks for its PIN, read from --pin-file (mode 0600 or stricter) or from the terminal, never from an argument.

theca create --fs exfat and theca serve (with --mount) are described in Serving and mounting.

Slots and caches (v0.6.0)

  • theca slots list and theca slots remove list the key slots and remove one by the factors that open it (go-theca/theca#5). In the library: Container.RemoveFactors(remove, keep), SlotsOf, Slots and ErrLastWay. A removal that would leave the keep set with no other slot is refused before any write.
  • Since v0.17.0 --remove and --keep also take the key: password+fido2 and recovery+fido2 (any order; a key opens a slot only with one partner). A set with the key touches it once, and the slot it opens must exist and must not be among the removed ones, so a key that is not the one enrolled here, or that holds no Theca credential, is refused before any write. To make the key mandatory: theca slots remove vault.theca --password-file pw --remove password --keep password+fido2. A container only the key opens also needs --fido2 to be opened (a second touch). Library: Container.RemoveFactorSets(remove, keep [][]Factor) and KeyPairs.
  • The metadata block cache and the Merkle node cache of an open container are bounded (#6): OpenOptions.CacheBytes and CreateOptions.CacheBytes, default 64 MiB. Clean entries are evicted least-recently-used and wiped; dirty ones are pinned until commit; an evicted entry is authenticated again when read. Close wipes the caches.

Later releases

  • v0.6.1: go-filesystems/smb v0.16.1, with per-source connection caps (32 per source, 16 pre-auth; loopback is not exempt, and the limit is far above one Finder client) and a zone-id fix.

  • v0.7.0: AES-256-CTR runs through go-encryptions/ctr (round keys expanded once, one kernel call per sector, no allocation; Zeroize wipes the round keys), and Argon2id through go-encryptions/argon2, the x/crypto/argon2 code with a NEON kernel on arm64. See the performance section below.

  • v0.8.0: FIDO2 on Linux (go-gnulinux/fido v0.5.1, CTAP over hidraw) and on Windows (go-mswin/webauthn v0.5.0, webauthn.dll). The transport is chosen by GOOS. See “FIDO2 on each OS” below.

  • v0.9.0: a TPM rollback counter. See “Rollback counter” below.

  • v0.10.2: the share’s account name is random (theca- and 8 random base32 characters), which fixes a second mount failing on macOS. See Serving and mounting.

  • v0.24.0 (security, go-theca/theca#66): a counter that is asked for is required. A container whose header names no counter (made without one, or a copy from before counter rebind) is refused under --counter tpm with “this container has no rollback counter, but –counter tpm was asked: an older copy may have been restored”; theca.Open returns ErrCounterRequired when given a counter. close-on-lock fails closed: if the lock watcher cannot start, open fails, and --close-on-lock=false is the explicit opt-out. On Linux only logind’s signals about this process’s own session count, and a session already locked at start closes at once; a screen locker that tells logind nothing (bare i3lock, swaylock) is not seen. The loopback SMB share requires message signing. profile add refuses a line Parse would refuse.

  • v0.25.0 (security, go-theca/theca#68): the key material in memory.

    • The FIDO2 PIN and the recovery code are []byte, wiped after use like the password (Unlock.Recovery, RecoveryFactor, format.ParseRecoveryCode and the fido2 PIN callbacks changed type: a break for library callers). Two copies remain as an immutable string: the PIN at go-authn/fido’s PINToken, and the recovery code create prints.
    • theca _serve (the detached daemon) turns core dumps off and refuses debuggers before any key exists: on Linux RLIMIT_CORE 0 and PR_SET_DUMPABLE 0, on macOS RLIMIT_CORE 0 and PT_DENY_ATTACH, nothing elsewhere. A refusal is a warning on stderr, not a stop.
    • The master secret, the slot wrap keys and their cipher caches are locked in RAM (mlock). --mlock=auto (the default) warns once if the system refuses, --mlock=required makes a refusal an error, --mlock=off turns it off; open hands its choice to the daemon. Not locked: the AES round keys inside the CTR library, transient key-encryption keys on the stack, and the crypto/hmac pads.
    • Cost, single core, 15 interleaved rounds, macOS arm64: open 187 us (off) against 202 us (auto) with a test-size KDF; writing 2 MiB 3.14 s against 3.21 s; reading 8 MiB 3.06 ms against 2.96 ms. The load was slightly above 8, so read the ratios.

  • v0.10.3: FIDO2 fingerprint handling and the PIN fallback, with the new ErrUVLocked. See --fido2 above.

  • v0.10.0 and v0.10.1: theca counter rebind, NO_DA on new counters, the threat-model note, and a correction of v0.9.0’s recovery advice. See “Rollback counter” below.

  • v0.18.0: the rollback counter is pinned to the TPM it was made on; a counter on another TPM is refused. See “Rollback counter” below.

  • v0.20.0: theca profile, open, close and status: one command and one touch, closing on lock. See “Daily use” above.

Rollback counter (v0.9.0 to v0.18.0) 

theca create vault.theca --size 1G --counter tpm   # defines an NV counter, binds the container to it
theca info   vault.theca --counter tpm             # rollback protected: true (TPM NV counter ...)
theca info   vault.theca --counter tpm --accept-rollback   # accept an older copy on purpose (loud); needs the counter
theca counter rebind vault.theca --counter tpm --tpm-owner-auth-file owner   # the counter is gone: bind to a new one
  • --counter tpm defines a TPM 2.0 NV counter (go-tpm2/tpm2 v0.9.0) and binds the container to it. The counter advances once per mount, not per commit: an older copy of the container is refused with ErrRollback before anything is written. The copy taken during the current session is the window that stays open (DESIGN section 5.4).
  • Every command that opens the container needs --counter tpm again (and --tpm-auth-file if you set one), and opens the file read-write, because a mount rebinds the header. A protected container opened without the flag is refused with a message naming it. Without --counter tpm, a container is not protected: an older copy would be accepted.
  • --tpm-device is a device path, or unix:SOCKET for a software TPM. The default is /dev/tpmrm0 on Linux and tbs: (TPM Base Services, through go-tpm2/devtpm’s OpenTBS) on Windows since v0.26.0. macOS has no TPM and says so unless a device is named. Windows is not measured on a real TPM: on a Windows 11 VM without a TPM the real tbs.dll answers TBS_E_TPM_NOT_FOUND, and no counter has been run there.
  • When the counter is gone (the owner undefined the index, or TPM2_Clear, a BIOS reset or a reinstall removed it; the index has no POLICY_DELETE, which would need platform authorization), the container cannot be opened. The message says so and names the recovery, theca counter rebind FILE --counter tpm --tpm-owner-auth-file F (v0.10.0). Earlier text, including this page’s, said --accept-rollback would help; it does not, because it needs a counter that exists and is ahead of the container. rebind needs the factors that open the container and the TPM owner password. It defines a counter (at the recorded handle if free, else the first free one), binds the header to it and increments it. Since v0.10.1 a still-present old counter is deleted first: otherwise a copy made just before the rebind would still open with it. Rollback protection then restarts from that moment; nothing is checked against the old counter. An old copy of the container shows the same refusal as a reset TPM: do not rebind to open one.
  • New counters carry TPMA_NV_NO_DA (go-tpm2/tpm2 v0.10.0), so a wrong authValue file does not count towards the TPM’s lockout. Counters made by v0.9.0 are still opened.
  • The TPM is pinned (v0.18.0, go-theca/theca#39). create and counter rebind record in the authenticated header the identity of the TPM the counter is on: the digest of the Name of its endorsement key (the ECC P-256 EK template of the TCG EK Credential Profile, created transiently and flushed, never persistent; go-tpm2/tpm2 v0.11.0). Every mount compares it before reading the counter; a counter on another TPM is refused, naming both identities (first 6 bytes in hex) and the recovery. info shows counter TPM identity: <hex>. It needs the endorsement authValue to be empty (the default). Containers made before v0.18.0 carry no identity: they open as before, with a warning at every mount, until theca counter rebind pins them (it replaces the counter, so protection restarts from that moment).
  • Threat model, by attacker. Someone who replaces the container file with an older copy: stopped, as before. Someone who brings another TPM (a fresh software TPM, a replaced TPM) and defines the same index on it at the old bound: stopped since v0.18.0, not in a container made earlier and not rebound. Someone who controls the TPM in use (the host of a virtual TPM, a program standing between theca and the TPM): not stopped; the identity names a TPM, it does not prove the TPM answering is that one, because the EK public is not secret. Someone who holds a copy of the TPM’s state (a software TPM’s state directory, a VM snapshot) holds its endorsement seed: not stopped, and the counter rolls back with the state. A bus interposer forging the answers of a discrete TPM: not stopped. TPM2_NV_Certify under an attestation key would authenticate the answers; it was weighed and deferred (DESIGN section 5.4.1), because it does not change the outcome against the other attackers.
  • Measured against a user-space software TPM (swtpm) on a Linux machine, not a hardware TPM. The counter has not been run against a hardware TPM.

Security notes

The threat model is DESIGN section 1. The places where the code differs from, or fixes the details of, the design are in its section 19, the implementation log; the FIDO2 design and its trade-offs are in HARDWARE-KEYS.md section 9, “H2 revised”.

Known limits, as the repository states them:

  • Rollback protection is opt-in. Every command that opens a container says whether it is protected against rollback. Without --counter tpm it is not, and an older copy would be accepted. With it, protection needs a TPM 2.0 (Linux only for now), and the TPM’s owner can delete the counter (a denial of service, not a rollback; theca counter rebind recovers, and protection restarts).
  • FIDO2 was measured on a real key on macOS only (a YubiKey 5, firmware 5.7.4). The Linux and Windows routes exist but are not measured on a real key.
  • A reader of the FIDO2 salt can test password guesses. The salt that a key is asked for is derived from the partner factor, so for whoever reads it (a forged authenticator, a leaked log) it is a password verifier, at Argon2id cost per guess. The salts are wiped after each call and never logged (DESIGN section 19, I21).
  • Revoked factors: older copies of a container still open with a factor that was removed (DESIGN section 19, I15).
  • Tree area: a container at rest is indistinguishable from random except the Merkle tree area, which shows how sparse the container is (DESIGN section 19, I11).

Performance

Theca is measured against C references on one core with go-scikit/refbench: libsodium for XChaCha20 and Argon2id, OpenSSL for AES-256-CTR and HMAC-SHA-256. The procedure and the cases are in bench/README.md. Ratio is Go time divided by reference time; below 1 is faster. Both runs are on commit 6d515c5 with go1.27.4, libsodium 1.0.22 and OpenSSL 4.0.2, from 2026-11-15. Medians in ns/call; the full tables, with quartiles and allocation counts, are docs/perf-table.md and docs/perf-zen4-table.md.

A gap in a row includes Theca’s own per-sector setup cost, which is a cost of the design and not of the language.

Since v0.7.0 (the table above is the v0.1.0 run), per the CHANGELOG: Argon2id on the Apple M4 Max went from 1.54 to 0.73 of libsodium, and AES-256-CTR is 1.03x and the sector tag 1.04x OpenSSL there (#8 and #9 stay open). On Zen 4 (the AMD Ryzen 9 7950X, v0.7.0): AES-256-CTR is 0.97 of OpenSSL, the sector tag 0.98, and Argon2id 0.25 of libsodium. On amd64 the Argon2id code is x/crypto’s unchanged, and libsodium’s 265 ms there was confirmed by a C control program on the same core, so that row stands as a measurement of libsodium on this machine. The control is recorded in the bench README on main: a C program calling crypto_pwhash (Argon2id, t=3, m=64 MiB, one lane) pinned to the same core gives 265 ms with the registry build and 265 to 271 ms with the legacy pkgx build of libsodium 1.0.22 (2026-11-17). The Zen 4 table is docs/perf-zen4-table.md (refbench, commit 20299a8 = v0.7.0, 1-minute load 0.31 to 0.47, OpenSSL 4.0.2): AES-256-CTR 0.97 of OpenSSL, sector tag 0.98, XChaCha20 0.44 and Argon2id 0.25 of libsodium, Seal and Open 0.53. The M4 Max table is docs/perf-table.md. The XChaCha20 row has no libsodium control yet. The M4 Max tables are in docs/perf-table.md at that tag.

Rows of the v0.1.0 run that were slower, each tracked as an issue (the changelog says #8 and #9 stay open after v0.7.0, and #10 is the Argon2id one):

  • #8: Sector/AES-256-CTR is slower than OpenSSL.
  • #9: Sector/Tag (HMAC-SHA-256) is slower than OpenSSL.
  • #10: Argon2id is slower than libsodium on arm64 (no NEON kernel in x/crypto/argon2).

Caveat on the Zen 4 libsodium rows. On that machine libsodium’s XChaCha20 and Argon2id run far below their usual AVX2 speed (about 440 MB/s, and 4 times slower than Go’s Argon2id). The registry’s libsodium may be built without its SIMD code. Until a control with another libsodium build settles this, the “faster” verdicts in those two rows are not claims.
