theca

theca

Theca is an encrypted container format in pure Go, with a library and a command line. The library gives an io.ReaderAt and io.WriterAt over the logical volume, and the command line creates, inspects, verifies, imports and exports containers. Since v0.2.0 it also serves the files inside over SMB and mounts them: see Serving and mounting.

The same logic is a library package, share, since v0.3.0: see Library: share.

Release: v0.9.0 (tag v0.9.0 of go-theca/theca; install with go install github.com/go-theca/theca/cmd/theca@v0.9.0). What changed is in the CHANGELOG at v0.9.0. The format may still change before v1. This page is written from that tag; where it differs from the repository, the repository wins. Its links to the repository’s design documents still point at tag v0.1.0, and the performance tables below were measured on the v0.1.0 commit.

What it is

From the README:

  • authenticated sectors: XChaCha20 xor AES-256-CTR, with HMAC-SHA-256;
  • a Merkle tree over the sector tags, and a write-ahead journal;
  • no magic bytes;
  • keyslots opened by a password (Argon2id), a recovery code, or both;
  • an optional hardware rollback counter.

The design, its threat model, the sources it rests on and the decisions taken are in docs/DESIGN.md; section 0 is a one-table summary.

Factors

A container is opened by one of three factors:

  • a password, stretched with Argon2id;
  • a recovery code, printed once by create and never stored;
  • a FIDO2 security key, which is never a factor alone: it always pairs with the password or with the recovery code.

The policy is chosen at creation. --policy any (the default) lets the password alone, or the recovery code alone, open the container. --policy 2of3 needs two of the three: password and recovery code from the start, and a FIDO2 key (enroll-key) then pairs with each.

Command line 

go install github.com/go-theca/theca/cmd/theca@latest

theca create vault.theca --size 1G            # asks the password twice, prints the recovery code once
theca info   vault.theca                      # unlock and describe
theca verify vault.theca                      # authenticate every sector and tree node
theca import vault.theca --password-file pw --offset 0 < disk.img
theca export vault.theca --password-file pw > disk.img

theca enroll-key vault.theca --recovery-file rc   # pair the key with the password and the recovery code
theca info vault.theca --fido2                    # password + key
theca info vault.theca --recovery-file rc --fido2 # recovery code + key
  • Secrets never go in arguments or environment variables. The password is read from the terminal with echo off, or from --password-file. The recovery code is read from --recovery-file. Both files must be regular files that only their owner can read (mode 0600 or stricter); anything else is refused.
  • create prints the recovery code once, on standard output. If you redirect it to a file, that file gets your umask (often 0644): restrict it, or better, write the code down on paper.
  • import reads its data from standard input, so it needs --password-file or --recovery-file. It is not one atomic transaction: on an error, the bytes written before the error are kept.
  • enroll-key makes one discoverable credential on the key (relying party theca, credProtect 3, hmac-secret) and pairs it with the password, and with the recovery code too when --recovery-file names it. The key is touched twice: to register, then to confirm.
  • --fido2 adds the attached key to an unlock. A key without a fingerprint asks for its PIN, read from --pin-file (mode 0600 or stricter) or from the terminal, never from an argument.

theca create --fs exfat and theca serve (with --mount) are described in Serving and mounting.

Slots and caches (v0.6.0)

  • theca slots list and theca slots remove list the key slots and remove one by the factors that open it (go-theca/theca#5). In the library: Container.RemoveFactors(remove, keep), SlotsOf, Slots and ErrLastWay. A removal that would leave the keep set with no other slot is refused before any write.
  • The metadata block cache and the Merkle node cache of an open container are bounded (#6): OpenOptions.CacheBytes and CreateOptions.CacheBytes, default 64 MiB. Clean entries are evicted least-recently-used and wiped; dirty ones are pinned until commit; an evicted entry is authenticated again when read. Close wipes the caches.

Later releases

  • v0.6.1: go-filesystems/smb v0.16.1, with per-source connection caps (32 per source, 16 pre-auth; loopback is not exempt, and the limit is far above one Finder client) and a zone-id fix.

  • v0.7.0: AES-256-CTR runs through go-encryptions/ctr (round keys expanded once, one kernel call per sector, no allocation; Zeroize wipes the round keys), and Argon2id through go-encryptions/argon2, the x/crypto/argon2 code with a NEON kernel on arm64. See the performance section below.

  • v0.8.0: FIDO2 on Linux (go-gnulinux/fido v0.5.1, CTAP over hidraw) and on Windows (go-mswin/webauthn v0.5.0, webauthn.dll). The transport is chosen by GOOS. See “FIDO2 on each OS” below.

  • v0.9.0: a TPM rollback counter. See “Rollback counter” below.

On Linux /dev/hidraw* belongs to root on a stock system: install a udev rule giving your user access to FIDO keys (libfido2’s 70-u2f.rules); theca then says “a security key is attached but this user cannot open it” instead of “no key”. On Windows, hmac-secret needs WebAuthn API version 6 (Windows 11 reports 9), and when several Theca credentials are on the key, Windows has the person pick one.

Rollback counter (v0.9.0) 

theca create vault.theca --size 1G --counter tpm   # defines an NV counter, binds the container to it
theca info   vault.theca --counter tpm             # rollback protected: true (TPM NV counter ...)
theca info   vault.theca --counter tpm --accept-rollback   # rebind an older copy on purpose (loud)
  • --counter tpm defines a TPM 2.0 NV counter (go-tpm2/tpm2 v0.9.0) and binds the container to it. The counter advances once per mount, not per commit: an older copy of the container is refused with ErrRollback before anything is written. The copy taken during the current session is the window that stays open (DESIGN section 5.4).
  • Every command that opens the container needs --counter tpm again (and --tpm-auth-file if you set one), and opens the file read-write, because a mount rebinds the header. A protected container opened without the flag is refused with a message naming it. Without --counter tpm, a container is not protected: an older copy would be accepted.
  • --tpm-device is a device path, or unix:SOCKET for a software TPM. The default is /dev/tpmrm0 on Linux. macOS has no TPM and Windows (TBS) is not supported yet (go-tpm2 has no TBS transport): both say so unless a device is named.
  • Stated limit: the owner of the TPM can delete the counter, and TPM2_Clear removes it. That is a denial of service, not a way back: a redefined counter starts above every earlier count, so the container is refused until --accept-rollback (DESIGN section 19, I22).
  • Measured against a user-space software TPM (swtpm) on a Linux machine, not a hardware TPM. The counter has not been run against a hardware TPM.

Security notes

The threat model is DESIGN section 1. The places where the code differs from, or fixes the details of, the design are in its section 19, the implementation log; the FIDO2 design and its trade-offs are in HARDWARE-KEYS.md section 9, “H2 revised”.

Known limits, as the repository states them:

  • Rollback protection is opt-in. Every command that opens a container says whether it is protected against rollback. Without --counter tpm it is not, and an older copy would be accepted. With it, protection needs a TPM 2.0 (Linux only for now), and the TPM’s owner can delete the counter (a denial of service, not a rollback).
  • FIDO2 was measured on a real key on macOS only (a YubiKey 5, firmware 5.7.4). The Linux and Windows routes exist but are not measured on a real key.
  • A reader of the FIDO2 salt can test password guesses. The salt that a key is asked for is derived from the partner factor, so for whoever reads it (a forged authenticator, a leaked log) it is a password verifier, at Argon2id cost per guess. The salts are wiped after each call and never logged (DESIGN section 19, I21).
  • Revoked factors: older copies of a container still open with a factor that was removed (DESIGN section 19, I15).
  • Tree area: a container at rest is indistinguishable from random except the Merkle tree area, which shows how sparse the container is (DESIGN section 19, I11).

Performance

Theca is measured against C references on one core with go-scikit/refbench: libsodium for XChaCha20 and Argon2id, OpenSSL for AES-256-CTR and HMAC-SHA-256. The procedure and the cases are in bench/README.md. Ratio is Go time divided by reference time; below 1 is faster. Both runs are on commit 6d515c5 with go1.27.4, libsodium 1.0.22 and OpenSSL 4.0.2, from 2026-11-15. Medians in ns/call; the full tables, with quartiles and allocation counts, are docs/perf-table.md and docs/perf-zen4-table.md.

The Apple M4 Max run was at a 1-minute load of 7.22 to 7.59 (gate 8.00); the Zen 4 machine is an AMD Ryzen 9 7950X pinned to one CPU, at a load of 0.16 to 0.35. Both runs are marked valid. A gap in a row includes Theca’s own per-sector setup cost, which is a cost of the design and not of the language.

Since v0.7.0 (the table above is the v0.1.0 run), per the CHANGELOG: Argon2id on the Apple M4 Max went from 1.54 to 0.73 of libsodium, and AES-256-CTR is 1.03x and the sector tag 1.04x OpenSSL there (#8 and #9 stay open). On Zen 4 (the AMD Ryzen 9 7950X, v0.7.0): AES-256-CTR is 0.97 of OpenSSL, the sector tag 0.98, and Argon2id 0.25 of libsodium. On amd64 the Argon2id code is x/crypto’s unchanged, and libsodium’s 265 ms there was confirmed by a C control program on the same core, so that row stands as a measurement of libsodium on this machine. The control is recorded in the bench README on main: a C program calling crypto_pwhash (Argon2id, t=3, m=64 MiB, one lane) pinned to the same core gives 265 ms with the registry build and 265 to 271 ms with the legacy pkgx build of libsodium 1.0.22 (2026-11-17). The Zen 4 table is docs/perf-zen4-table.md (refbench, commit 20299a8 = v0.7.0, 1-minute load 0.31 to 0.47, OpenSSL 4.0.2): AES-256-CTR 0.97 of OpenSSL, sector tag 0.98, XChaCha20 0.44 and Argon2id 0.25 of libsodium, Seal and Open 0.53. The M4 Max table is docs/perf-table.md. The XChaCha20 row has no libsodium control yet. The M4 Max tables are in docs/perf-table.md at that tag.

Rows of the v0.1.0 run that were slower, each tracked as an issue (the changelog says #8 and #9 stay open after v0.7.0, and #10 is the Argon2id one):

  • #8: Sector/AES-256-CTR is slower than OpenSSL.
  • #9: Sector/Tag (HMAC-SHA-256) is slower than OpenSSL.
  • #10: Argon2id is slower than libsodium on arm64 (no NEON kernel in x/crypto/argon2).

Caveat on the Zen 4 libsodium rows. On that machine libsodium’s XChaCha20 and Argon2id run far below their usual AVX2 speed (about 440 MB/s, and 4 times slower than Go’s Argon2id). The registry’s libsodium may be built without its SIMD code. Until a control with another libsodium build settles this, the “faster” verdicts in those two rows are not claims.
